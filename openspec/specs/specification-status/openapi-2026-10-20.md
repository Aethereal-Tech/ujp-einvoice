## What it settles

- **The error body of `einvoice_api`.** Every response is a `GenericAPIResponse`:
  - `success` (boolean);
  - `createdDate` (date-time);
  - `errorStatus`, an `ErrorStatusBean` of `errorCode`, `errorMessage` and `errorPropertyMap` (a map from property
    to a list of messages).

  `errorCode` is a closed enum of 72 codes: E1000–E1024, E4000–E4027 and E5000–E5019. That this namespace has no
  E10xxx and none of the JSON Receiver's E1025–E1035 confirms the per-API namespacing.
- **Status.** `current-status` answers a `DocumentCurrentStatusResponse` whose `docStatus` is an `InvoiceStatus`. It
  carries `euid`, `statusCode`/`statusName`, the document number and dates, `docNetAmount`, `docVatAmount`,
  `docGrossAmountR`, `docAvansAmount`, `docFinalAmount`, the four TINs, `docType`/`docTypeName`, and every comment and
  reason code (void, reject, correction). The status codes come back as served strings, as `design.md` decision 8
  plans.
- **The catalogues are served, dated and versioned.** Each of these has a `GET` plus a `/{date}` variant:
  - tax indicators: `code`, `categoryCode`, `vatImpact`, `vatType`, `taxGroupCode`, `note`, `validDateFrom`/`To`;
  - tax groups: `percent` is an integer;
  - document types: `needSignature`, `hasReference`, `isReferenceMandatory`, `currencyType`;
  - reference document types, void reasons, correction reasons, payment types and statuses.

  `doc-type-x-tax-indicator` says which indicators each kind admits. This argues for `TaxIndicators` being a dated
  snapshot that a consumer can refresh, not a constant set (decision 4).
- **`server-time`** answers `{timestamp}`.
- **The signed request** is `{jws, nativeHostAppVersion?}`. The examples' JWS header is `{"alg":"RS256"}` (truncated
  in the example). The headers `X-EDB`, `X-EUJP-ID` and `X-SERIAL-NUMBER` are required on JWS calls.

## What it does not settle

- **The invoice document itself.** The document is sent to the JSON Receiver
  (`/JSONReceiver/api/v1/sales-invoices/send`), which this description does not cover, and no description of it is
  linked or found. `InvoicePayload.payload` is an opaque string, so the field-level shape and optionality of
  `document` stay sourced from the per-type tables and the 08.10 examples.
- **The JSON Receiver's own error body.** It is likely the same `GenericAPIResponse`, but that is not stated.
- **The production base URL.** The only server is `efakturatest`.
